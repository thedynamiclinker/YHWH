# What we want YHWH to do

Build a highly capable assistant that feels natural to talk to while it
handles the tedious digital parts of life. Jason and Ramya are making
this for themselves first. They will use it heavily, notice what is
confusing, and let that experience guide what becomes a product.

The desired personality comes from their Yahweh in We The Nameless.
Privately, he can be scruffy, irreverent, funny, and conversationally
unprofessional. Work that goes out on the user's behalf should be
competent, accurate, and appropriate to the recipient. The character
earns his place by getting things done.

## The experience

Talking should be a useful way to operate the computer. A request such
as “put that in the file from before and open it” should work using the
context already available. The system should find the file, choose the
appropriate execution tools, complete the work, and verify the result.
The user should be able to keep talking while longer work runs.

Conversation can include digressions, jokes, interruptions, and several
people. The assistant should retain the pending task through that noise,
distinguish action requests from context, and say when a referent or
speaker is uncertain. Jason and Ramya want to test this by changing
speakers and directions midstream.

Useful context should compound. Their hypothesis is that knowing the
people, projects, preferences, and reasons behind requests will let the
assistant act effectively from much shorter instructions. Preserve
substance from the conversation in readable files, including the
interesting reasoning and jokes. Accurate condensation should keep
uncertainty and disagreement visible.

Written output matters as much as speech. Lists, prompts, explanations,
and decisions need a record people can inspect and revisit. Provide
visible text alongside spoken questions. Save requested material in
the vault, and open files with the desktop's default application unless
a particular program is named.

## Make the app learnable

A new user should immediately see a useful walkthrough and learn by
completing a concrete task. Example Company and the existing local
drafts provide a starting environment. Tips should remain discoverable
in a secondary location, with a persistent “Don't show this again”
choice for the popup.

Replace sample integrations gradually with real connections and useful
actions. Real account connections are future work. The immediate focus
is understanding the workflow and improving its presentation.

Every moment where Jason or Ramya cannot understand the app is evidence
for the next design change. Their own daily use is the feedback loop.

## Build with what already works

Use existing models, Codex, the shell, desktop programs, and ordinary
files to make this useful quickly. Training a new language model from
scratch is outside the current plan. The proof of concept already
exists. The work ahead is a long sequence of improvements to capability,
context, and user experience.

The routing between conversation and implementation should feel smooth.
They want the capable part of the system to carry out the request
without requiring them to identify which component owns the tools.

Verification should match the claim. A launcher accepting a command
does not establish that an editor window appeared. A file move should
be checked at both locations. The recent display-permission problem and
editor tabs showing moved files made those distinctions concrete.
